# Converter handoff notes

Working notes for picking this back up later. Not user-facing docs (those
live in `src/content/docs/en/v0_1/reference/conversion/index.md`, which is
the actual policy spec this code implements).

## Module map

- `src/fraction.mjs` — exact `{n, d}` rational arithmetic. Everything timing-related uses this, never floats, since `<group>` divisions aren't bounded to powers of two.
- `src/resolve.mjs` — structural resolver. Reuses `renderer/src/parse.mjs` for header/parts/music, adds its own walk of `<structure>` for pass counts. Exposes `resolve(source) -> { ...parsed, playOrder, resolveSection, unroll, unrollLyrics }`.
  - `resolveSection(partId, sectionId, totalPasses)` — per-pass note timelines, for MusicXML (which writes one part at a time, following `<structure>`'s own repeat/ending semantics).
  - `unroll(partId)` — the whole piece for one part, fully concatenated across every pass, flattened. This is what MIDI wants, and it's also what the current MusicXML writer uses (see below).
  - `unrollLyrics(lyricPartId, targetPartId)` — a lyric part's syllables as `{onset, text}`, in the same global cursor units as `unroll(targetPartId)`'s notes, by walking the *target's* own line/measure/beat structure rather than the lyric part's - see the lyrics bug entry below for why that coupling is load-bearing.
  - Both `resolveSection`/`unroll` return notes with exact-fraction `onset`/`duration`, plus `measureBoundaries` (cumulative onset of each measure's end) so a consumer can slice the flat note list into measures without re-deriving line/beat structure itself.
  - The critical invariant a consumer can rely on: no resolved note ever crosses a measure boundary. `foldMeasure` guarantees the last kept item in a measure ends exactly at that measure's own length. This is what makes bucketing notes into `<measure>` elements by comparing onsets to `measureBoundaries` safe.
  - `foldMeasure` is stack-aware: it takes an optional `siblingAttacks` list (onsets, local to the measure, of every note a sibling row of the same `stack` plays there) and uses it to cap a note's open-ended extension - but only an open-ended one, never a note whose own row's next note follows with no gap. `resolveSection` computes this by finding the calling part's stack-mates (`parsed.parts` filtered by matching `stack`, excluding `type="lyric"`) and threading their same-position measures through `resolveSectionPass`. See "Rests" in the docs for the exact rule and why the distinction matters (it's what keeps deliberate interlocking - one hand holding while the other moves fast - from getting flattened).
  - `effectiveLine(sectionMusic, number, pass, isLyric)` — the line a part actually plays at a given position: the base line, with any `<ending>` override applied, and (for a notated part) a completely empty override measure swapped back for the base line's own measure at that position - see ending.md's "Unchanged measures" and the bug entry below. Used by `resolveSectionPass` (both the calling part's own line and every stack sibling's) and `resolveLyricSectionPass` (the target line only - a lyric line's own empty measure keeps its unrelated "nothing sung" meaning and is never substituted this way).
- `src/pitch.mjs` — `<tuning>` resolution + one note's absolute pitch (MIDI number and MusicXML step/alter/octave from the same semitone value, so both export targets agree). Shared by both targets.
- `src/musicxml-durations.mjs` — a resolved note's fraction duration → MusicXML `<duration>`/`<type>`/`<dots>`/`<time-modification>`, tied across multiple `<note>` elements if needed. Load-bearing insight: a duration's own reduced denominator tells you what tuplet it needs (strip factors of 2; the odd part left over, if any, is the tuplet's `k`) — this holds regardless of *how* the duration arose (plain group member, one that absorbed a sibling rest, a plain note whose decay got cut short by a following group's early pickup, or a *rest* that's the kept thing before anything has sounded).
- `src/to-musicxml.mjs` — the actual XML assembly. See "Known scope-narrowing" below — it currently always unrolls repeats rather than emitting native barlines/voltas. Also resolves lyric-part pairing (`resolveLyricPairs`/`resolveLyricTexts`/`resolveLyricAssignments`) and attaches `<lyric>` elements to whichever note is sounding at each syllable's onset.
  - `recut(notes, boundaries)` is the stage between the resolved timeline and the XML: it re-cuts one member's notes against the *output's* measure grid, and everything about how the score reads comes out of it. It fills gaps with rests, merges consecutive rests, breaks a merged rest at the output's beat (not a note - a note is written as one value and tied), splits any event crossing a barline into tied pieces, and collapses a bar of pure silence into one `<rest measure="yes"/>`. Before it existed, a measure could simply come out short (a stack row with nothing more written, a decay a sibling's attack cut off) and readers flagged it as an incomplete measure — `assertMeasuresAreFilled` in the tests is the invariant that pins this down across every real file.
  - `<divisions>` is sized from the **re-cut** durations, not the resolved ones. Merging rests and splitting at barlines both produce fractions no single resolved note had (a 1/3-slot rest merged with a 1-slot one is 4/3, needing the 3:2 tuplet's `normal` in the tick base), so scanning the resolved notes would under-size the tick base and `decomposeTicks` would throw.
  - Two timeline settings sit on top of `recut`, both MusicXML-only: `downbeatShift` (default **on**, `--no-downbeat-shift`) moves every note one slot later so a Thai measure's counted last beat lands on a Western downbeat, and `trimLeadingEmptyMeasures` (default off) drops the leading measures nothing sounds in. Both reduce to one integer `offset` per output group, applied to note onsets and to the lyric map's keys alike (`resolveLyricTexts` takes the offset so its keys come out in output units — syllable matching itself still happens in resolved units, where the syllable onsets live). The trim count is computed across the whole ensemble, never per part, or the parts would desync.
- `src/ensemble-groups.mjs` — `groupParts(parts, splitStacks)`, factored out once both writers needed the identical stack-merging logic. Both writers must stay in lockstep here: if one changes how a stack becomes an output unit, so must the other.
- `src/to-midi.mjs` — Standard MIDI File (format 1) byte assembly: one meta/tempo track plus one track per output part/stack, built with hand-rolled VLQ delta-time and chunk encoding (no external MIDI library, consistent with this project's general no-new-dependencies style). Repeats are *always* fully unrolled (Standard MIDI has no native repeat concept at all, so there's no "simple case" the way MusicXML has). `<annotation>` text and `<nathap>` aren't carried into meta events - `resolve.mjs`'s `playOrder` doesn't capture their content, only `<chan>`'s value and `<bpm>`, so only those two make it into meta events. A stray `sound`-bearing note in a part not declared `type="unpitched"` (a real inconsistency `example-lao-duang-duean.txml` turned out to have), or the reverse, is *decided per note*, not per part/group: it warns and converts as a rest rather than crashing or sounding on the wrong channel - see the `sound !== declared type` bug below.
- `dump.mjs` — CLI (`node converter/dump.mjs <score.txml> [partId]`) that prints the resolved note timeline per part/section/pass. This is the tool of choice for eyeballing correctness against a real piece before trusting a unit test's hand-derived expected values — it's how both real bugs below were actually found.

## Known scope-narrowing (deliberate, not forgotten)

`to-musicxml.mjs` always **unrolls** every pass of every repeated section into
its own plain measures, rather than the documented default (native repeat
barlines + volta endings for a `<repeat>` that wraps exactly one section).
Sound and pitch are fully correct either way; a repeated piece just doesn't
*look* repeated yet — this is Task #2 in the project's task list, deferred
because it needs a `<structure>`-tree walk (classify each `<repeat>` as
"wraps one section" vs. "wraps several siblings", the latter needing the
documented unroll-that-scope fallback) that hasn't been built. No example
file currently exercises the "wraps several siblings" case.

Lyric parts (`type="lyric"` in `<ensemble>`) now export to MusicXML `<lyric>`
elements (see reference/conversion's "Unpitched and lyric parts" for the
policy: default first-lyric-to-first-part pairing, `--lyrics-map` for an
explicit one, `--no-lyrics` to disable). This is MusicXML only — MIDI export
still skips lyric parts with a warning, since v0.1's scope for this task
never covered MIDI lyric meta-events (a real, not-yet-decided extension, not
an oversight).

Unpitched parts get one fixed notehead position (a placeholder), since sound
codes have no defined mapping to a staff line/space.

## Real bugs found so far, all by testing against real files, not just unit tests

1. **Group member positioning** (in `resolve.mjs`, before this writer existed): the original onset formula spread group members forward from the beat; the actual rule (matching `renderer/src/geometry.mjs`'s `arrivals()`, which already had it right) is "beats anchor to the right" — the *last* member lands on the beat, earlier members lead up to it. Found via `dump.mjs` output against a real piece, by ear/eye from the user, not by a failing test — the unit tests at the time all had their expected values derived from the same wrong mental model.
2. **`<divisions>` sizing scanned only each stack's first row** (in `to-musicxml.mjs`): a `<group>` living only in a stack's second row was invisible to the piece-wide `ticksPerSlot()` scan, since the scan only looked at `group.members[0]`. Crashed outright (`cannot represent a duration of 0.5 ticks at 2 divisions`) on `tutorial7-ensemble.txml`. Fixed by scanning every member of every group. **Lesson: always test-convert every real example/corpus file, not just the one or two picked for manual review** — this is what caught it.
3. **Tuplet-scaled notes/rests need an explicit `<tuplet type="start"/>`/`<tuplet type="stop"/>` bracket, not just `<time-modification>` on each note — this took two attempts to actually fix.**
   - First symptom: a *kept* rest (real silence before anything has sounded) landing inside a group's bracket had no `<time-modification>` at all — the rest-handling branch of `noteElements` discarded the `tuplet` field `encodeDuration()` returned. Fixed by emitting it for rests too.
   - That fix alone did **not** resolve the user's reported MuseScore error (`Incomplete measure ... Found: 25/48, Expected: 2/4`), because the actual cause was one level deeper: `<time-modification>` on every note is necessary but not sufficient — a reader also needs `<tuplet>` start/stop markers in `<notations>` to know which *contiguous run* of notes forms one bracket. Without them, MuseScore couldn't tell that a **tied continuation note** (the second half of one logical note split across a printed-value boundary, e.g. a triplet-quarter tied to a triplet-16th) was still inside the same bracket as the note before it, and reverted that one note to its unscaled face value — throwing the measure's total off by exactly the tuplet's own scaling. Confirmed the mechanism numerically before touching code: `6+6+2+8+3=25` (the last note's plain, unscaled 16th value used instead of its scaled `2`) matched the reported error exactly.
   - Real fix: added `assignTupletBrackets()` in `to-musicxml.mjs`, which flattens a staff's notes into tied-duration segments first, then does a pass marking the first/last segment of each contiguous same-ratio tuplet run with `start`/`stop`. Also fixed `<note>` child element order while in there — the DTD wants `<staff>` before `<notations>`, which the original code had backwards (harmless for well-formedness, wrong per spec).
   - **Debugging technique worth repeating**: when a notation program reports a numeric discrepancy like `Found: 25/48`, don't just eyeball the XML — extract the exact note sequence for the flagged measure/staff and brute-force which specific "what if this one value were different" hypothesis reproduces the reported number exactly. That's what pinned this down (see git history around this note for the reproduction script) rather than more rounds of "does this individually look right."
   - Regression test: `converter/test/to-musicxml.test.mjs`, "every tuplet bracket across every real example and corpus file is properly matched" — a general invariant (every `<time-modification>`-tagged segment sits inside a matched start/stop bracket, per measure per staff) checked against all 29 real/corpus files, not a hand-built synthetic case. Prefer this style of test over a narrow synthetic repro when the triggering fraction arithmetic is fiddly to hand-derive — real files already exercise it.
4. **Rest extension resolved per row, even within a stack** — not a coding mistake like the others, a genuine gap in the design that the user caught by ear after the tuplet fix above, on the exact same `example-khaek-borathes.txml` measure (s2 measure 3: `<group><note pitch="ฟ"/><rest/><rest/></group>` in one row, `<group><rest/><note pitch="ซ"/><note pitch="ล"/></group>` in the sibling row). ฟ absorbs its own group's trailing rests and, with nothing else written in its own row, used to ring for a full extra beat (5/3 slots) - but the sibling row attacks (ซ) only 1/3 of a slot in. Confirmed with the user this should be a real policy: a `stack` is one physical instrument (see `link` in `group.md`), so a decaying note's relevance ends at *any* row's next attack, not only its own row's. Implemented in `resolve.mjs`: `foldMeasure` takes an optional `siblingAttacks` list and caps a note's `end` there, but *only* when the extension is already open-ended (a rest was absorbed, or the row has nothing left written that measure) - never when the row's own next note follows with zero gap, since that's an explicit, deliberate spacing choice (e.g. one hand holding a note while the other plays a fast independent line) that a sibling's activity must not override. `resolveSection` computes the calling part's stack-mates from `parsed.parts` (matching `stack`, excluding `type="lyric"` per `group.md`'s own rule that a lyric row has no beat position for this to reach) and threads their measures through. Documented in the docs' "Rests" and "Stacked instruments" sections, not just here, since it's a real semantic rule about what a `<rest>` means in a stack, not a converter implementation detail. Regression tests in both `resolve.test.mjs` (the capped case, and a control case proving a non-stacked part is unaffected) and the existing `to-musicxml.test.mjs` real-file stress test.

5. **`isUnpitched` decided per part/group instead of per note** (in `to-midi.mjs`, found the same way as bug 2 - the real-file stress-test loop, this time on `example-lao-duang-duean.txml`): `addNoteEvents` checked `group.members[0].type === "unpitched"` once for the whole group and used that to decide whether *every* note in it should read `.pitch` or `.sound`. `example-lao-duang-duean.txml`'s `khim2`/`khim3` parts (declared plain `type="pitched"`, no `type` attribute at all) each turn out to have a couple of stray `<note sound="x"/>` elements mixed into otherwise normal pitched lines - `resolvePitch(null, ...)` crashed on them. Fixed by deciding pitched-vs-percussion **per note** (`note.sound != null`), with a warning on mismatch rather than a hard failure - consistent with this format's general "soft violations warn, they don't invalidate the document" convention (see note.md's own redundant-octave/discarded-attribute warnings).
   - **First fix (superseded)**: a mismatched note was routed to the percussion channel regardless of its group's own assigned channel. The user later asked for this to be revisited: a mismatched note isn't real percussion either, so playing it on channel 9 was still a guess, not a defensible reading. **Current behavior**: a mismatched note converts as a rest instead (no note event at all), in both `to-midi.mjs` and `to-musicxml.mjs` (the MusicXML writer had the same per-note gap - `describeNote` decided unpitched-vs-pitched purely from `note.sound`'s presence, ignoring the part's own declared type - fixed the same way, for the same reason, once the MIDI side was revisited). `resolvePercussionNotes` (MIDI) and the `isUnpitched` used for MusicXML clef/key selection now only need to consider groups actually declared `type="unpitched"`, since a mismatched note never reaches the percussion-note table or gets a pitched notehead anymore.
   - **This is very likely a real, previously unnoticed mistake in `example-lao-duang-duean.txml` itself**, not a converter design question - unlike bug 4 above. `khim2`/`khim3` are overwhelmingly normal pitched khim lines (120+ `pitch=` notes each) with just one or two `sound="x"` notes mixed in, which reads like a copy-paste leftover or a placeholder rather than an intentional unpitched effect. Nothing catches this today: `check-corpus.mjs` only runs against `public/corpus/`, not `renderer/examples/`, and there's no automated check that a `sound`-bearing note's containing part actually declares `type="unpitched"`. **Still not fixed in the source file** - the converter now degrades gracefully around it (silently drops those two notes as rests, with a warning), but the file itself still has the data quality issue. Exact lines: `example-lao-duang-duean.txml:653` and `:784`.

6. **Lyrics: no defined pairing to a notated part** (design gap flagged when the MIDI writer was built, closed for MusicXML once the user confirmed the approach): the docs already say pairing is left to an `<annotation>` or the arranger's own knowledge, not something the format states structurally, so a converter has to pick a policy. Landed default: first lyric part (ensemble order) pairs to the first output group; `--lyrics-map` (a `{lyricPartId: notatedPartId}` JSON file) states an explicit pairing instead, by part id or a specific stack row's id; `--no-lyrics` disables lyric export. `resolve.mjs` gained `unrollLyrics(lyricPartId, targetPartId)`, deliberately reusing the *target* part's own line/measure/beat structure and cursor progression (not the lyric part's) so a syllable's global onset lands in the exact same units as `unroll(targetPartId)`'s notes - see `resolveLyricSectionPass`'s doc comment for why that coupling is load-bearing, not incidental. Each syllable then attaches (`to-musicxml.mjs`'s `attachTarget`) to whichever note is actually sounding at its onset first; failing that, the nearest note before it (appending, joined with a space if more than one syllable lands the same way); failing that too (nothing has played yet), the nearest note after it. Only a target with no note anywhere leaves a syllable dropped, with a warning. Scope is MusicXML only for v0.1; MIDI karaoke-style lyric meta-events were considered and deliberately deferred as new, undocumented scope rather than folded into this task.

7. **`<ending>`'s empty-measure shorthand didn't exist, and `resolve.mjs` silently mishandled the invalid input that looked like it** (found testing the lyrics feature against `example-lao-duang-duean.txml`, then generalized with the user): that file's ranad-ek part has a `<ending pass="2">` whose line 4 leaves measures 1-6 completely empty (`<measure number="1"></measure>`, no children), only writing real content for measures 7-8. Before this fix, `resolve.mjs` read a measure's beat count as `beats.length` unconditionally, so those six 0-beat measures collapsed the cursor to zero across all of them - not a lyrics-specific bug, `doc.unroll("ranad-ek")`'s own note timeline was corrupted the same way, independent of anything lyrics-related. The user's read of the source data - the empty measures were meant to say "unchanged from the base line", a shorthand for not having to retype six measures that don't vary - turned into a real, deliberate feature rather than a one-off fix, since `<ending>`'s existing Conformance rule ("corresponding measures must have the same beat count... only the notes may vary") explicitly required real content, making the file's empty measures invalid under the *old* spec. No RelaxNG change was needed - `<measure>` already permits zero children structurally via the lyric-measure-content branch of its `<choice>`, so this was a prose-Conformance change, not a grammar one. Landed as `resolve.mjs`'s `effectiveLine()`: a completely empty override measure in a **notated** part (lyric parts keep their own, different "nothing sung" meaning for an empty measure, unaffected) is swapped back for the base line's own measure, span markers included (the user's call: "inherited wholesale", not requiring the arranger to still restate a span's `stop` in an otherwise-unchanged measure). Renderer needed **no code change at all** - `grid.mjs`'s share/arrival math already no-ops cleanly on an empty `beats` array (traced through by hand: `total=0` only ever divides into values nothing iterates over), so an unchanged measure was already drawn as an empty cell in the ending's own standalone block, which is also the user's chosen rendering treatment (deliberately not resolving the inherited content there - a reader cross-references the base line above for what actually plays). `check-corpus.mjs`'s `checkEndingsAndSpans` got the matching exception (both the beat-count-mismatch check and the span open/close matching, which now merges inherited measures - markers included - before walking). New corpus fixture: `public/corpus/valid/ending-inherits-empty-measure.txml`. `example-lao-duang-duean.txml` itself was deliberately left untouched - its empty measures are valid and correctly interpreted now that the feature exists, so no edit was needed there after all.

8. **The MusicXML output was a transcript of the resolved timeline, not a score** (reported by the user as "the notation does not look quite natural", and fixed by `recut()` above): every slot of real silence printed as its own eighth rest; any gap the resolved timeline didn't cover printed as nothing at all, leaving the measure short; a tie chain of three or more printed values marked its middle segments `stop` with no matching `start`; and a rest split across printed values was given `<tie>`s, which a rest can't have. The first is what the user noticed; the rest fell out of writing the invariant test (`assertMeasuresAreFilled`) that a re-cut stage made checkable — running it against the pre-fix writer reported ~625 problems across the 31 real files, most of them short measures in stacked parts. **Lesson repeated from bug 3**: an invariant checked over every real file finds things a hand-built case never suggests looking for.

9. **A part that leaves out a section desynced its own cursor from the rest of the ensemble** (reported by the user from real-world use: a section missing from a part's own output entirely, and - worse - a *different* part's later section landing on the wrong measures, "as if the next section moved up to meet the skipped one"). `section-ref.md` explicitly allows a part to have no `<section-ref>` at all for a section it sits out; `unroll()`'s section loop, on hitting that, just `continue`d - no notes, but also no cursor advance and no `measureBoundaries` entries for the section's own span. Every other part's later sections still needed *some* measures to exist there, so on export the silent part's later content printed starting right after its last real measure, overlapping whatever the other parts were actually playing at that point rather than lining up with it. This is exactly `to-musicxml.mjs`'s "stacked rows disagree on measure count" warning path in disguise for a stack's *first* row (its boundaries, borrowed by the whole group, were short - `prepareGroup`'s `raw = members[0].measureBoundaries`), and silent corruption with no warning at all for two parts that aren't stacked together, since each gets its own independent grid. Also corrupted MIDI export the same way, more severely - MIDI has no measure grid to desync, just a wrong absolute tick for every note after the omitted section. Root-caused, not guessed at: reproduced with a two-part, two-section score where the second part omits the first section, and confirmed via `dump.mjs`/`unroll()` output that the second part's cursor stayed at 0 instead of jumping to the first section's length. Fixed in `resolve.mjs`: a new `referenceSectionResolution(sectionId, totalPasses)` finds any *other*, non-lyric part that does reference the missing section - guaranteed by `section-ref`'s own Conformance rule to agree exactly on line/measure/beat counts with every other part that references it, so any one is a valid stand-in - and borrows only its shape (`length`, `measureBoundaries`), never its notes, to advance the omitting part's cursor and measure grid correctly while contributing a real silence (left for `recut()`'s existing gap-filling to print as a rest). `unroll()` and `unrollLyrics()` both had the identical bug independently (the latter's own comment used to say it deliberately "matched `unroll`'s own handling" - true, but of a bug, not a policy) and both got the same fix; a lyric part's own reference to a section it's paired to doesn't count as a shape donor, since a lyric measure holds words, not beats. This turns out to fully close the "different measure counts" item below - the only way two parts referencing the same sections could ever disagree was one of them silently failing to advance through a section it lacked. Regression tests in `resolve.test.mjs` (cursor/boundary alignment directly) and `to-musicxml.test.mjs` (the exported grid, plain and lyric-paired). `khaek-borathes-test.txml` and `tutorial7-ensemble.txml` now convert with matching measure counts and no warning.
   - **Sharper variant, same root cause, caught by the user asking about a second, separate-looking symptom**: "the downbeat shift" (`--no-downbeat-shift` is the opt-out) not extending a note properly. A part whose omitted section is the piece's *last* one (it simply stops playing before the piece's actual end, not a middle section) had its own `boundaries` end exactly at its last real measure - which `recut()`'s barline-crossing logic treats as license to *not* tie a decay across (the same rule that, correctly, avoids buying a whole extra measure for a decay nobody strikes at the piece's real end - see the shift tests in `to-musicxml.test.mjs`). So a decaying note in that part's actual last written measure, which the shift pushes across a barline, got silently clipped with no `<tie>` at all instead of continuing into the next measure - dropping sound, not just misplacing measures. Confirmed by diffing the exact same input against the pre-fix code: before, `<note><pitch><step>B</step><octave>4</octave></pitch><duration>3</duration><type>quarter</type><dot/></note>`, no tie, silently short; after, the same note carries `<tie type="start"/>` and its continuation appears, tied, at the front of the next measure. Fixed by the same change above, since it's the identical short-`boundaries` cause; regression test added to `to-musicxml.test.mjs` ("a part that stops playing before the piece's actual end still ties its last decay under the downbeat shift").

10. **A shift-promoted note never revisited how far it could ring, even once bug 9 was fixed** (user-reported from a real file, `example-lao-duang-duean.txml`'s ranad-ek, s1 line 1, measures 4-5, which has no omitted section at all - this is a distinct issue from bug 9, not a leftover symptom of it). Measure 4 ends `...<rest/><note pitch="ซ"/><rest/><note pitch="ด"/>`; measure 5 is `<rest/><rest/><rest/><note pitch="ร"/>`. `ด` is measure 4's own last beat, `openEnded` per bug 9's new flag - nothing caps it but the barline. The shift promotes it to measure 5's own downbeat (the whole point of the setting), and measure 5 is otherwise real silence until ร on its own last beat - but `resolve.mjs`'s cap, computed once before the shift exists, still only gave `ด` a single slot; the reader saw a short note followed by two rests' worth of unmotivated silence, on a downbeat with nothing else happening for the rest of the bar. Root-caused with the user by walking through exactly what "measure 5" in the shifted output actually contains (source measure 4's last beat plus source measure 5's leading rests - not source measure 5's own content, which lands one measure later still). This raised a real design question, resolved with the user before implementing: should the "own measure" a note's ring is capped by mean the *source* (Thai) measure, as `resolve.mjs` computes it today - or the *output* (shifted) measure, once the shift has moved the note somewhere else? Landed: the output measure, but only for `resolve.mjs`'s `openEnded` notes specifically (never a note closed by something real - its own row's next note, or a sibling's, both already correct and untouched) - MIDI and `--no-downbeat-shift` output keep exactly today's behavior, since nothing moves there.
    - `resolve.mjs` itself stays shift-agnostic (it has no idea a shift is coming, and shouldn't need to) - `foldMeasure` still stops an `openEnded` note's `duration` dead at the barline, same value as always. The decision moved downstream: `to-musicxml.mjs` gained `extendOpenEnded(notes, boundaries)`, run per member in `prepareGroup` after the shift is applied and before `recut()`. For a note flagged `openEnded`, it finds which output measure the note's *natural* (shifted, still-uncapped) end falls into - deliberately the natural end, not the shifted onset, since a note that had already absorbed several rests (so its unshifted duration already ran most of a beat) needs that longer reach accounted for, or the wrong, too-early measure gets picked and the note gets capped shorter than it already legitimately was. It then extends the note to the earlier of that measure's own end, or the next real attack anywhere later in the same row (rests in between are skipped over - they're the "unmotivated silence" this exists to remove).
    - Deliberately bounded to one measure past where the note already stopped, matching the shift's own fixed one-slot move, rather than hunting arbitrarily far ahead for the next attack - a note that finds nothing in the one newly-available measure stays exactly as short as `resolve.mjs` left it. Also deliberately doesn't re-run sibling-attack capping into that newly-claimed measure - a stacked `openEnded` note can currently claim room a sibling's *next-measure* attack would have capped it out of, since `resolve.mjs`'s sibling capping only ever looked within a single measure to begin with. Flagged as a known, narrow gap rather than fixed, since it needs sibling data threaded through the post-shift step too and no real file has shown it mattering yet.
    - Verified directly on the reported file: measure 5 now prints `ด` as one half note filling the whole bar (no tie needed - it lands squarely inside the new measure's own boundaries), rather than an eighth note followed by an eighth rest and a quarter rest. Also re-verified every other shift test by hand, since this touches the same mechanism: a note that legitimately crosses into a measure where something *does* attack still ties correctly at exactly that attack's onset, unchanged from before (see "a note the shift pushes across a barline is split and tied" in `to-musicxml.test.mjs`); a note with nothing at all after it anywhere in the piece, promoted into a genuinely new tail measure, now fills that whole tail measure too, rather than a bare eighth followed by padding rests (see "the downbeat shift moves every note a slot later" in the same file, updated to match). Regression tests: `resolve.test.mjs` pins the `openEnded` flag itself (set only when nothing, including a sibling, capped the note short of the barline); `to-musicxml.test.mjs` adds a dedicated case for a note filling an entire otherwise-empty measure it was shifted into, distinct from the barline-crossing-into-real-content case already covered. Every real example/corpus file still converts cleanly (no crashes, no new warnings) and the existing "every measure filled, every tie closed" real-file invariant test still passes across all four option combinations.

**Pattern across all of these**: this codebase's tests are only as good as
the mental model they were hand-derived from. When the mental model itself
is wrong (or incomplete — see bug 3's first, insufficient fix), tests built
on it agree with the bug. Real-file conversion (`dump.mjs` output, or
actually opening generated `.musicxml`/`.mid` in a notation program or DAW)
is what has caught every real bug so far, including two crashes that only
one specific real file out of 29 ever exercised — keep doing that before
trusting a green test suite alone, especially after touching timing/duration
logic. A green suite after a fix is necessary but not sufficient proof the
fix is complete — re-test the *original* reported symptom too, not just the
mechanism you first suspected.

## What's next

Everything else (the MusicXML writer, the MIDI writer, and `convert.mjs`)
is built and tested. What's left:

- **Task #2, the only remaining implementation gap**: native repeat barlines + volta endings for the simple case (a `<repeat>` wrapping exactly one section, however deeply nested via further repeats around just that section) in `to-musicxml.mjs`. Needs a `<structure>`-tree classifier ("does this repeat wrap one section or several siblings") that doesn't exist yet. Until this lands, MusicXML export always fully unrolls every repeat instead - correct sound, just not native engraving. No example file currently exercises the "wraps several siblings" fallback case either, so that path is still just a documented policy, not implemented or tested.
- **Fixed** (was: "parts can come out with different measure counts in one file"): see bug 9 above. `to-musicxml.mjs`'s "stacked rows disagree on measure count" warning and its accompanying note-dropping code path (`prepareGroup`) are now dead in practice - every real/corpus file converts with no such warning - but were left in place as a defensive check rather than removed, since nothing currently proves a stack's rows can't disagree some other way not yet found.
- **Still open, not a task yet**: `example-lao-duang-duean.txml`'s stray `sound="x"` notes (bug 5 above) - a real content mistake in that example file. The converter now degrades gracefully around it (rest, with a warning) rather than crashing, but the file itself still hasn't been fixed. Exact lines: `:653` and `:784`. (Its *other* apparent issue, the empty `<ending>` measures, turned out not to need a file fix at all - see bug 7.)
- **Possible follow-up, not requested yet**: MIDI karaoke-style lyric meta-events (bug 6 above) - MusicXML lyric export is done, MIDI deliberately isn't; scope, timing model (probably the same "attach to the sounding note's onset tick" idea, minus the "which note" lookup since a MIDI lyric event doesn't need one), and target track placement would all need deciding first.
- **Possible follow-up, not requested yet**: the static renderer's own span-matching (`renderer/src/parse.mjs`'s `resolveSpans`, called separately on an `<ending>`'s own lines) doesn't know about "unchanged measure inherits its markers too" (bug 7) - it only ever sees the ending's own literal, unresolved XML, so a span reaching into an inherited/blank measure in the ending's *own drawn block* just won't find its `stop` there and silently won't draw (per parse.mjs's existing "dangling marker" handling - no crash, just an incomplete curve in that one, deliberately-blank block). `check-corpus.mjs` and `resolve.mjs` both merge correctly for validation/conversion; only the renderer's own display of the ending's own separate block has this minor gap, and only for a span that both reaches into an unchanged measure *and* is drawn inside that specific block.
- `convert.mjs` is a thin CLI over `resolve.mjs` + `to-musicxml.mjs`/`to-midi.mjs`: `--to musicxml|midi` (required), `--out`, `--tuning`, `--split-stacks`, `--instrument-map`/`--percussion-map` (JSON files), `--no-lyrics`/`--lyrics-map`/`--no-downbeat-shift`/`--trim-leading-empty-measures` (MusicXML only).
